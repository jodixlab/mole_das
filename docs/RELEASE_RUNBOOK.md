# MOLE-DAS Release Runbook

This runbook defines the standard release path for MOLE-DAS executable packages.
Use this process instead of manually copying release folders, editing handoff files,
or updating OneDrive pointers by hand.

## Release Model

The release process is intentionally split into two commands:

1. Build and validate the package from a clean workspace.
2. Apply operator approval, tag the release, and promote it to backup.

The first command is automated validation. The second command is the controlled
human signoff and publication step.

## Prerequisites

- Work from the D: development repository:

```powershell
Set-Location "D:\mole_development_environment\2026_04_09_001"
```

- Confirm the branch is clean except for the untracked `RELEASES\` evidence tree:

```powershell
git status --short --branch
```

- Confirm there is adequate free space. Prefer E: scratch because C: and D: are
often tight during PyInstaller builds.

```powershell
Get-PSDrive C,D,E | Select-Object Name,@{Name='FreeGB';Expression={[math]::Round($_.Free/1GB,2)}}
```

## Command 1: Clean Release Workflow

Run the clean workflow from the D: repo and place scratch on E:.

```powershell
$commit = (git rev-parse --short HEAD).Trim()
$stamp = Get-Date -Format "yyyyMMdd_HHmmss"
$scratch = "E:\mole_release_workflow_official\scratch_${commit}_$stamp"
$artifact = "D:\mole_development_environment\2026_04_09_001\RELEASES\clean_release_workflow_${commit}_$stamp"

powershell -NoProfile -ExecutionPolicy Bypass `
  -File "D:\mole_development_environment\2026_04_09_001\scripts\run_clean_release_workflow.ps1" `
  -RepoRoot "D:\mole_development_environment\2026_04_09_001" `
  -ScratchRoot $scratch `
  -ArtifactOutDir $artifact
```

The clean workflow must end with `Status: PASS` in:

```text
<artifact>\clean_release_summary.txt
```

Required automated gates include:

- Unit tests
- Launcher/report integration smoketest
- UI help audit
- Release gate with strict hashes
- Windows executable bundle build
- Packaged acceptance
- Recipient installer validation from the collected installer ZIP
- Artifact contract generation
- Initial go/no-go decision

At this stage, the go/no-go decision is expected to be `PENDING_OPERATOR` until
the operator approves package review signoff.

## Command 2: Finalize Approved Release

After reviewing the clean workflow evidence, run the finalizer. This is the only
approved path for signoff, tagging, handoff metadata, OneDrive promotion, and
latest-release pointer updates.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File "D:\mole_development_environment\2026_04_09_001\scripts\finalize_approved_release.ps1" `
  -ArtifactDir $artifact `
  -RepoRoot "D:\mole_development_environment\2026_04_09_001" `
  -ApprovedBy "User" `
  -ApprovalBasis "Operator issued GO after review of clean workflow PASS, packaged acceptance PASS, recipient installer validation PASS from the collected installer ZIP, release package hashes, artifact contract PASS, and package_review_signoff gate." `
  -Notes "Operator GO for approved release package." `
  -ApprovalDate (Get-Date -Format "yyyy-MM-dd")
```

Use `-ForceBackup` only when intentionally replacing an existing OneDrive backup
folder for the same artifact directory. Use `-ForceTag` only when correcting a
tag that points to the wrong commit.

## Final Acceptance Criteria

The finalized release is acceptable only when these files report `PASS`:

```text
<artifact>\release_go_no_go_decision.json
<artifact>\release_artifact_contract.json
<artifact>\RECIPIENT_VALIDATION_FROM_INSTALLER.json
<artifact>\PROMOTION_TO_BACKUP_SUMMARY.json
<artifact>\FINAL_RELEASE_SUMMARY.json
```

The final go/no-go decision must be:

```text
status = PASS
overall_decision = GO
```

The release tag must point to the package commit:

```powershell
$tag = "release/<package_label>"
git rev-list -n 1 $tag
```

The result must match the commit in:

```text
<artifact>\latest_verified_release_v1.json
```

## Output Locations

The D: artifact folder is the primary release evidence location:

```text
D:\mole_development_environment\2026_04_09_001\RELEASES\clean_release_workflow_<commit>_<stamp>
```

The OneDrive executable backup is generated by the finalizer:

```text
C:\Users\User\OneDrive - Encino Environmental Services, LLC\mole_development\executables\clean_release_workflow_<commit>_<stamp>
```

The latest approved release pointers are written to both:

```text
D:\mole_development_environment\2026_04_09_001\RELEASES\LATEST_APPROVED_RELEASE.json
D:\mole_development_environment\2026_04_09_001\RELEASES\LATEST_APPROVED_RELEASE.md
C:\Users\User\OneDrive - Encino Environmental Services, LLC\mole_development\executables\LATEST_APPROVED_RELEASE.json
C:\Users\User\OneDrive - Encino Environmental Services, LLC\mole_development\executables\LATEST_APPROVED_RELEASE.md
```

## Do Not Do Manually

Do not manually:

- Edit `release_go_no_go_decision.*`
- Edit `operator_go_no_go_checklist.*`
- Edit `APPROVED_RELEASE_HANDOFF.md`
- Move or recreate release tags
- Copy approved release folders to OneDrive
- Update `LATEST_APPROVED_RELEASE.*`

Use `finalize_approved_release.ps1` for those actions so tag validation, hash
verification, and promotion summaries stay consistent.

## Recovery Rules

If command 1 fails, do not finalize. Fix the failure, commit if source changed,
and rerun the clean workflow into a new artifact directory.

If command 2 fails before promotion, inspect the error, fix the metadata or tag
problem, and rerun command 2.

If command 2 fails during promotion, rerun with `-ForceBackup` only after
confirming the artifact directory is the intended approved release.

Never use `git reset --hard` or manual folder deletion as part of release
recovery unless explicitly approved and the target path has been verified.
